# 文档写作、更新与校验

本页分三块：**写作标准**、**更新流程**、**校验方法**。写作与更新规则只有本页一份；用户手册的专用规则见 [user-doc-verification.md](user-doc-verification.md)。

---
## 一、文档写作标准

### 1. 文件模板

#### 1.1 子文档模板（多文件篇目）

```text
# 标题（`模块/目录`）
## 本篇涉及的文件      ← doc-trees.mjs 生成
## 综合概述            ← **定位** / **公共逻辑** / **局限**
## 详细说明            ← 逐文件条目
## 注意事项            ← 跨文件风险
```

逐文件条目统一采用 5 段结构，全文一致：

| 段 | 内容要求 |
| --- | --- |
| 定位 | 一句话说明职责，以及在界面或流程中的位置 |
| 对外接口 | 组件：Props / Emits / Slots / Expose；函数：签名与返回；路由：方法 + 路径 + 入参/出参；模块：导出清单 |
| 内部实现 | 关键函数或处理步骤（函数名、入参、作用），不逐行解释 |
| 依赖与调用方 | 依赖关系与调用来源 |
| 注意点 | 注意事项、约束、红线 |

- 「综合概述」只写文件夹级共性：定位（覆盖哪类文件、属于哪一层）、公共逻辑（共享流程 / 数据流 / composable / store / 接口）、局限（本篇不覆盖的内容，并链接兄弟文档）；不重复模块 README 的整体机制。
- 「注意事项」只写跨文件风险：事务顺序、撤销登记、鉴权挂载、公共接口变更影响、产物顺序、环境依赖等；单个文件自己的注意点留在该文件条目里；没有跨文件风险就不加这一节。
- 单文件、纯清单篇目可只保留目录树与明细，不为结构凑数。

#### 1.2 子模块模板（模块级 README）

```text
# 模块名（`目录/`）
整体机制        ← 职责、运行方式、关键机制（跨文件部分）
文件索引        ← 目录树 + 子文档表（链接到子文档）
模块标准        ← 该层必须遵守的约束
维护入口        ← 指向本页
```

适用对象：[main-process/README.md](./main-process/README.md)、[backend/README.md](./backend/README.md)、[frontend/README.md](./frontend/README.md)、[testing/README.md](./testing/README.md)。

#### 1.3 专题类模板

```text
# 专题名
## 本篇涉及的文件                          ← doc-trees.mjs 生成
## 整体设计 / 专题总览                     ← 设计 / 规范类用前者，机制 / 测量 / 流程类用后者
## 详细设计 / 详细说明                     ← 按子主题分组，不按文件罗列
## 验证与注意事项
```

- 实现位置就近写进对应子主题，文末不再放全量索引表；细则见 [topics/README.md](./topics/README.md)。
- 分层文档只写清单与标准，跨层机制写进 `topics/`，同一件事只写一遍。

### 2. 写作规则

#### 2.1 词语与链接规则

- **所有代码文件引用都写成 Markdown 链接**（路径相对当前文档所在目录），不只写文件名；函数名、常量、IPC 通道等仍用反引号。
- **英文代码标识就在原处配中文说明**：首次出现时紧跟括号写清含义（如 `data-theme`（主题标识）、`applyTheme()`（应用主题函数））；同一文档重复出现可简化。不要集中做英文对照表，读者应当在该标识出现的同一句里就能看到中文。代码围栏外的正文行若出现反引号标识，整行不能只有英文（`dependencies/licenses.md` 的许可证原文豁免）。
- **禁用词**：开发文档禁止「什么 / 怎么做 / 为什么 / 之类 / 约定」五类设问或模糊表述，全部文档禁止「约定」；改写为「动作 / 设计理由 / 校验项 / 标准」等具体说法。
- **字段标签统一加粗**：条目内的「定位」「对外接口」「内部实现」「使用方」「入参」「校验」「撤销」等标签写成 `**定位**：` / `**对外接口**：`，全文一致。
- **模块之间与文末都加分隔线**：每个 `##` 模块（第一个除外）之前空一行、写 `---`、再空一行；文件末尾也以空行 + `---` 收尾。由校验脚本检查。
- **前端组件的「对外接口」不能只列名字**：`props` / `emits` / `slots` / `expose` 每个都要用中文说明用途，`props` 标默认值，`emits` 标 payload 形状；内部实现只写会影响外部行为的交互机制（滚动、键盘/IME、拖拽、时序、清理），纯展示组件可只写定位、接口与使用方。示范见 [components/ai.md](./frontend/components/ai.md) 的 `AiComposer`。
- **后端路由写「处理标准」，不写源码翻译**：每个接口至少写方法 / 路径 / 职责；写操作标注「涉及的表 / 是否登记撤销」。复杂接口（注册登录、导出恢复、加密转换、AI、撤销等）按「入参校验 → 写表与事务 → 撤销 → 副作用 → 失败与局限」展开；跨层机制只给链接，不逐行解释源码。示范见 [backend/routes.md](./backend/routes.md) 的 `POST /register`。
- **内容须与源码一致**：无法从源码确认的内容不写入。

#### 2.2 图表规则

- **流程图统一用 Mermaid**：流程、时序、架构关系写成 ` ```mermaid ` 代码块（GitHub 在 README / Issue / PR / Wiki 中原生渲染），图内节点文字用中文；每张图前后保留一句中文说明，保证在不支持 Mermaid 的渲染器（终端、部分简易预览器）里仍能读懂主干。
- **跨文件篇目开头画「本篇涉及的文件」目录树**：只列本篇涉及的代码文件，从仓库根目录一路画到文件；单文件篇目同样从仓库根画到该文件。由 [`doc-trees.mjs`](../../testjs/tools/doc-trees.mjs) 生成，标记 `<!-- doc-tree:start/end -->` 之间可重复刷新。
- **目录树、组件层级清单用等宽文本树**：Mermaid 没有目录树类型，硬画可读性更差。

## 二、文档更新

### 1. 文档更新流程

**维护标准**：

- 新增、改名、删除文档时**必须**同步更新 [README.md](./README.md) 的目录与交叉链接，不留死链；尚未创建的文档只写路径并标「规划中」，不加链接。
- 跨层标准变更（IPC 通道名、HTTP 路由、安全通道协议）需要三层文档同批更新。
- 依赖增删要同步 `dependencies/`；新增测试脚本要同步 `testing/`；细节口径分别以各包 `package.json` 与 `testjs/README.md` 为准。
- 新增/删除/移动代码文件后重跑 `node testjs/tools/doc-trees.mjs`，刷新各篇「本篇涉及的文件」树。
- 用户手册的写法与维护另见 [user-doc-verification.md](user-doc-verification.md)。

**执行顺序**：

1. **改代码前**：在 `doc/README.md` 目录里找到对应文档，先读现状。
2. **改代码后**：按下方映射表更新文档的清单 / 标准；新增、删除或移动代码文件后，跑 `node testjs/tools/doc-trees.mjs`。
3. **跑校验**：`npm run docs:verify`；失败项会直接指出「哪个文件未覆盖 / 哪个路由缺 / 哪个依赖版本不符」。
4. **补叙述**：行为、时序、注意事项这类内容人工补（脚本不管）。
5. **记账**：在「维护记录」追加一行日期 + commit + 改动内容。
6. **提交前**：`npm run docs:verify` 必须为 0；建议接入 CI 或 pre-push。

### 2. 文档更新映射表

| 改动类型 | 需同步更新 |
| --- | --- |

| 新增/删除 service、改导出 | `backend/services.md` |
| 改表结构、连接/密钥策略 | `backend/data-layer.md`、`topics/security.md` |
| 新增/删除主进程模块、改 IPC 通道 | `main-process/README.md`（模块表 + 通道）+ `topics/security.md` |

| 新增/删除/移动代码文件（目录调整、文件改名） | 对应文档条目 + `testing/tools.md`（若动的是工具脚本）；跑 `node testjs/tools/doc-trees.mjs` 刷新篇首目录树 |

## 三、文档校验

### 1. 可信度说明

| 层      | 内容                                                                 | 证明方式                                                       | 现状                   |
| ------ | ------------------------------------------------------------------ | ---------------------------------------------------------- | -------------------- |
| A. 事实层 | 文件是否存在、组件/页面/composable 清单、HTTP 路由、依赖版本与许可、关键计数、IPC 通道、npm 脚本、环境变量 | `npm run docs:verify`（机器，可复现）                              | 全绿                   |
| B. 标准层 | Props / Emits / 导出函数名 / 返回字段 / 默认值 / 调用方                           | 源码抽取 + 手动比对（`defineProps`、`module.exports`、`return {...}`） | 已逐个核对，脚本未覆盖          |
| C. 叙述层 | 实现理由、问题成因、时序 / 范围                                                  | 只能手动阅读源码与历史记录                                              | 按模块逐步核对，仍有不足（见第 3 节） |

**说明**：A 层可被机器证明；B 层是「抽取值 + 抽查」；C 层是「手动判断」，受到体量和更新周期的影响不能保证 100%与源码的情况相同，如果遇到文档和源码冲突的情况，请按照源码为准。

### 2. 自动化校验

```powershell
npm run docs:verify            # 30 类校验；失败退出码 1
node testjs/tools/docs-verify.mjs --json   # 机器可读
```

脚本读源码 / 读配置，**不修改任何文件**。

#### 2.1 格式自动化校验（8 类）

| 校验项 | 检查内容 |
| --- | --- |
| 文档内部链接 | 80 份（`doc/` 下 79 份 + 根 README）的相对链接目标都存在 |
| Mermaid 图结构 | 代码块围栏成对；` ```mermaid ` 块首行必须是 GitHub 支持的图表类型；图内必须有中文节点文字 |
| doc-tree 结构 | 31 份文档的篇首树：标记成对、缩进合法、树内路径真实存在 |
| 文档禁用词 | 开发文档禁止「什么 / 怎么做 / 为什么 / 之类 / 约定」，全部文档禁止「约定」 |
| 英文标识配中文 | 代码围栏外正文行带反引号时必须同行出现中文；`licenses.md` 豁免 |
| 字段标签加粗 | 固定标签必须是 `**定位**：` / `**对外接口**：` 形式 |
| 模块与文末分隔线 | 每个 `##`（除首个）前、以及文件末尾，都必须有一行 `---` |
| 用户手册结构 | 32 篇必须依次是 `## 前言` / `## 具体方法` / `## 相关篇目` / `## 维护记录`；前言三行齐全，块间与文末有 `---`，维护记录含版本/改动列 |

#### 2.2 内容一致性校验（22 类）

| 校验项 | 覆盖对象 |
| --- | --- |
| 源码覆盖（7 类） | 组件 76、页面 22（含拆分模块）、composable 26、utils 26、后端 98、主进程 26 + `inno/` 与安装器素材、构建配置 5 个，逐个在文档中出现 |
| 路由校验 | `routes/**` 实际注册的 214 条 `METHOD path`（含 `historyRoutes` 工厂） |
| 依赖校验 | 40 个直接依赖的名称 / 声明版本或安装版本 / 许可证标识 |
| 关键计数（6 类） | 组件 76 / 组合式 26 / utils 26 / `main.*.js` 21 / 后端依赖 12 / 页面 15，与源码统计比对 |
| npm 脚本 | 23 个脚本全部在根 README 出现 |
| 环境变量（2 类） | `.env` 键在 README 有说明；文档声明的 7 个运行时变量在源码里确实被 `process.env` 读取 |
| IPC 通道 | `ipc-channels.json` 的 86 个通道全部写入文档 |
| 用户手册索引 | `doc/user/` 32 篇（除 README）全部写入 `user/README.md` |
| 工具脚本覆盖 | `testjs/tools/` 12 个脚本全部写入 `testing/tools.md` |
| 测试脚本覆盖 | `testjs/units`、`behavior`、`smoke`、`probe` 共 57 个脚本全部写入 `testing/` 对应子页 |

### 3. 自动化校验的不足和注意事项

- 只证明**结构与清单**正确，不保证**叙述性描述**（例如某个函数的重试时机）准确。
- 新增/删除文件、新增路由、升级依赖后必须重跑；脚本失败会以非 0 退出码阻断。
- 发现的文档错误应当**同时修脚本覆盖不到的地方**（人工复核叙述），脚本只保证不再漂移。

| 位置 | 情况 | 后续动作 |
| --- | --- | --- |
| `backend/routes.md` 处理要点 | 路径/方法已对齐源码；**每个 handler 的校验顺序**是归纳描述 | 需要时按单接口深读 |
| `frontend/components/*` 内部函数 | Props/Emits 为源码抽取；内部行为部分是人工总结 | 改动这些组件时顺手补 |
| `testing/probe.md` | 用途按脚本名与 README 归纳，未逐个读文件头 | 需要复跑某探针时以文件头为准 |
| `topics/performance.md` | 数值是**历史实测**，本次未复测 | 改性能相关代码后跑 `testjs/probe` 更新 |
| `topics/design-and-interaction.md` | 设计取舍来自 CSS 注释与源码，动效时长按源码抄录；**没有截图视觉回归** | 改主题/动效后人工看一遍目标主题，或补截图基准 |
| `widgets.md` | 主体沿用既有文档，本次只做链接化与失效文件标注 | 改小组件时逐段复核 |
| Mermaid 图 | 只校验围栏闭合与首行图表类型，**不校验图内语法与语义** | 改图后在 GitHub 或支持 Mermaid 的编辑器里预览一次 |
| doc-tree 目录树 | 只校验标记、缩进与路径存在，**不校验描述文字与分组是否合理** | 改篇首树的说明文字时人工看一遍 |
