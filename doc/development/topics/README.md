## 2. 阅读路径

- **想理解一次完整请求 / 一次 AI 对话**：先读对应机制专题的「专题总览」，再按「详细说明」里的子主题顺序读。
- **想改主题、排版或动效**：读 `design-and-interaction.md`，其中「详细设计」按子主题拆分，末尾给出验证方式与红线。
- **想排查启动慢、内存高或包体过大**：读 `performance.md` 的「专题总览」定位口径，再按需看具体章节与文末测量方法。
- **想改打包或切分支**：读 `build-and-branches.md` 的「专题总览」与「验证与注意事项」。

## 3. 写作结构

专题类文档统一四段（内容不成立的段可省略）：

```text
## 本篇涉及的文件      ← doc-trees.mjs 生成，只列本篇涉及的代码文件
---
## 整体设计 / 专题总览  ← 定位、目标 / 口径、核心取舍、与兄弟文档的边界
---
## 详细设计 / 详细说明  ← 按子主题分 ###，不按文件罗列；实现位置就近写在对应小节
---
## 验证与注意事项      ← 改哪类代码要跑哪些校验、红线、已知软点
```

- 设计类（`design-and-interaction.md`）用「整体设计 / 详细设计」；机制、测量与流程类用「专题总览 / 详细说明」。
- 「详细说明」按**子主题**分组（如主题、日夜、排版、动效），不要按源码文件逐个罗列；文件级清单归分层文档。
- 实现位置优先写在对应子主题末尾（`**实现位置**：…`）；确需总表时，放在「详细说明」的最后一个小节，而不是文末。
- 每篇结尾保留一条 `---`，与开发文档其余篇目一致。

## 4. 局限与维护

- 不重复分层文档已有的文件清单、接口签名与维护规则，只给链接与跨层结论。
- 改代码后按 [文档写作、更新与校验](../dev-doc-verification.md) 的「文档更新映射表」更新对应专题。
- 新增专题时同步本页表格与 [开发文档目录](../README.md) 的「2.5 专题」；统计与死链由 `npm run docs:verify` 兜底。
