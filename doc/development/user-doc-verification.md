# 用户手册的写法与维护标准（`doc/user/`）

面向维护者：用户手册正文在 [`doc/user/`](../user/)，本页只规定写法、维护方式与两套文档的边界，普通读者可跳过。

## 1. 写法标准

1. **人称与语气**：统一第三人称，主语用「用户」「界面」「程序」，不出现「你 / 您」；不写「请」「必须」「不要」这类指令句，改为客观描述行为（「界面会……」「此时……会……」）或「建议……」。
2. **路径写法**统一为「位置 → 分组 → 项目」，用 `→` 连接，例如 `设置 → 主题设置 → 日夜模式`；不用「右上角那个按钮」这类位置描述。
3. **二级结构固定四块**：`## 前言` → `## 具体方法` → `## 相关篇目` → `## 维护记录`；块间空一行、写 `---`、再空一行，文件末尾同样以 `---` 收尾（与开发文档的分隔线规则一致，见 [dev-doc-verification.md](dev-doc-verification.md) 的写作规则）。
4. **前言三行**：适用对象 / 本篇解决的问题 / 前提条件，写成 `- **适用对象**：内容` 形式；不写其他内容。
5. **具体方法按主题分 `###`**：使用范围、界面结构、常用操作、易错与建议等；小节内可继续用 `####`。不强制「四段」，但每个操作要写清入口、步骤与结果。
6. **只用两种提示块**：`> **易错**`（会丢数据或不可撤销）、`> **建议**`（可选优化）。不写第三种提示样式。
7. **术语单点定义**：只在 03 名词表解释一次，其余篇目直接引用，不重复定义。
8. **截图克制**：每篇最多 2 张，只拍「找不到的那个按钮」；能用文字路径说清就不拍，避免发版重拍。
9. **不写实现细节**：不出现加密算法、IPC（进程间通信）、数据库表结构；最多一句「数据在本机加密存储」。需要细节时见[开发文档](./README.md)。

## 2. 维护标准

- **单一来源**：正文只放 `doc/user/`；应用内帮助页与 PDF 都从这里生成，不另写副本。
- **同步触发**：任何用户可见行为变更（按钮改名、流程变化、默认值变化）在同一个提交里改对应篇目；同时在 [dev-doc-verification.md](dev-doc-verification.md) 的「文档更新映射表」加一行「用户可见变更 → `doc/user/`」。
- **维护记录**：每篇文末一张小表（版本 / 日期 / 改动内容），不在正文里写变更史；小节标题固定为 `## 维护记录`。
- **首轮优先**：01、03、13、20、22、40、41、60 —— 不写就会被反复问、不敢用或会出事的部分。

## 3. 与开发文档的区别

| 用户文档（[`doc/user/`](../user/)） | 开发文档（[`doc/development/`](./README.md)） |
| --- | --- |
| 操作步骤、界面文案、结果与注意事项 | 文件职责、接口入参出参、表结构、依赖 |
| 受众为班主任 | 受众为维护者 |
| 一个操作一段话 | 一个函数一段说明 |
| 可以不给截图来源 | 需要标注源码路径 |
