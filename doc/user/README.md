## 三、写法约定

1. **人称与语气**：统一第三人称，主语用「用户」「界面」「程序」，不出现「你 / 您」；不写「请」「必须」「不要」这类指令句，改为客观描述行为（「界面会……」「此时……会……」）或「建议……」。
2. **路径写法**统一为「位置 → 分组 → 项目」，用 `→` 连接，例如 `设置 → 主题设置 → 日夜模式`；不用「右上角那个按钮」这类位置描述。
3. **每篇开头三行**：适用对象 / 本篇解决的问题 / 前提条件。
4. **正文固定四段**：使用范围 → 操作路径 → 结果长什么样 → 注意事项。
5. **只用两种提示块**：`> **易错**`（会丢数据或不可撤销）、`> **建议**`（可选优化）。不写第三种提示样式。
6. **术语单点定义**：只在 03 名词表解释一次，其余篇目直接引用，不重复定义。
7. **截图克制**：每篇最多 2 张，只拍「找不到的那个按钮」；能用文字路径说清就不拍，避免发版重拍。
8. **不写实现细节**：不出现加密算法、IPC、数据库表结构；最多一句「数据在本机加密存储」。需要细节时见开发文档。

## 四、维护约定

- **单一来源**：正文只放 `doc/user/`；应用内帮助页与 PDF 都从这里生成，不另写副本。
- **同步触发**：任何用户可见行为变更（按钮改名、流程变化、默认值变化）在同一个提交里改对应篇目；同时在 [../development/verification.md](../development/verification.md) 的「改动 → 文档映射」加一行「用户可见变更 → `doc/user/`」。
- **修订记录**：每篇文末一张小表（版本 / 日期 / 改了什么），不在正文里写变更史。
- **首轮优先**：01、03、13、20、22、40、41、60 —— 不写就会被反复问、不敢用或会出事的部分。
